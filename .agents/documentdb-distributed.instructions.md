# DocumentDB Citus distribution

Owns the Citus implementation under `oss/internal/pg_documentdb_distributed/` and its execution contracts. Load this guidance for affected routing, pushdown, remote payloads, hooks, placement, or distributed upgrades even when the changed files are in another component. A purely local OSS change may skip it after applying the shared boundary contracts in [DocumentDB backend selection](documentdb.instructions.md#instruction-selection).

## Transactional Node-Command Dispatch

- Use `ExecuteTransactionalCommandOnMetadataCoordinator()` for coordinator-routed commands. It reuses `ExecutePerNodeCommandCore()` and the dedicated data-schema `coordinator_routing` table's single coordinator placement to execute in the caller's transaction. `RunCommandOnMetadataCoordinator()` is a legacy autonomous-routing workaround, not an alternative to use for new code. Treat existing uses as migration debt: move them to the transactional function contract rather than preserving independent commits as compatibility behavior.
- Coordinator dispatch requires a completed cluster version of **1.3 or later**, enforced by `IsClusterVersionAtleast(DocDB_V1, 3, 0)`. This is a runtime cluster-version requirement, not a binary-version check. Do not migrate callers before the cluster upgrade completes and the routing anchor is provisioned; an installed binary or an existing table alone does not make this route available. Unsupported clusters fail explicitly; do not add an autonomous fallback.
- Versioned cluster initialization/upgrade actions create the empty, admin-owned routing table with `disallow_writes_check CHECK (false)` to reject inserts, grant SELECT to PUBLIC, and register it with Citus local metadata. It is not a reference table. An existing table is left untouched, including grants and registration; do not silently convert or repair it. A same-version `complete_upgrade()` skips provisioning, and the uninitialized-cluster skip policy remains unchanged. Public SELECT permits routing, not target execution authorization or public writes.
- Share the routing table name through the `CoordinatorRoutingTableName` extern in `api_hooks_def.h`, initially NULL. Set the literal once in `InitializeDocumentDBDistributedHooks()`, which the DocumentDB distributed initialization invokes. Creation, dispatch, and the planner use that same value; do not add a second macro, include internal headers from public OSS, or duplicate the literal.
- Autonomous command helpers do not enlist remote writes in the caller's transaction: a later failure can leave committed remote state that caller rollback cannot undo. Blind retries or compensating SQL are not atomic rollback. The old cron adapter also rethrew status/text failures as internal errors, losing the target SQLSTATE; preserve native target errors through transactional dispatch instead.
- Targets must be functions taking one BSON argument and returning BSON. They execute inside an atomic `SELECT`/`FunctionScan`, not a top-level `CALL`. Procedures have a different invocation/result contract, even without transaction control; internal commits or rollbacks additionally conflict with caller-owned atomicity and cannot run in this function execution context. Do not open an autonomous connection to bypass that restriction. Preserve the fixed calling convention rather than adding speculative arity, signature-validation, or nullable-result machinery.
- The dispatch SELECT is a protocol with the shard relation-path hook, not a row-reading query. Keep the worker function as its single target over the routing table. `ProcessWorkerDispatchQuery()` replaces the shard scan with a `FunctionScan` and injects the destination-local shard OID, so execution does not depend on table contents. Do not add `GROUP BY ()` or another aggregate to manufacture one result on an empty table; preserve the shape the hook recognizes.
- `command_node_worker()` always enables nested distribution for the duration of the target call because these DDL commands commonly dispatch further work. Restore the caller's GUC state on normal return and rely on transaction/subtransaction abort for error cleanup. Do not add `PG_TRY`/`PG_CATCH` without a cleanup obligation not already handled by that lifecycle.
- Keep the target's BSON argument unchanged. Do not reintroduce an `allowNested` option, an `_internal_arg`/`_internal_options` envelope, or framework options encoded in the function-signature field for this uniform policy. Establish a real per-command behavior difference before adding another parser or configuration path.
- For cross-node dispatch, send the qualified function signature and `InvalidOid` in the legacy function-OID slot. The third worker argument is a separate shard-OID placeholder filled by the receiving planner. Do not compare a physical routing shard's OID with the logical routing table's OID. Apply the [shared cross-node identity rules](documentdb-common.instructions.md#cross-node-object-identity).
- Direct `OidFunctionCall1()` or `FunctionCallInvoke()` does not perform SQL EXECUTE authorization. For caller-selected dispatch targets, resolve the destination-local function, check `PgProcAclCheckCompat(..., GetUserId(), ACL_EXECUTE)` unconditionally, then invoke directly. An initialized `FunctionCallInfo` is not a permission check; do not introduce a separate SPI execution path just to obtain one.
- Keep relation eligibility separate from worker rewriting and retain the data-schema gate. Attempt dispatch before returning for `!isShardQuery`; a non-collection relation qualifies only for `command_node_worker()` on the matched routing basename. Validate its generated suffix through `IsShardTableForRelation()` with a relation-name `StringView` and logical-name length; the distribution provider bounds-checks the offset before indexing and checks `_` plus nonempty decimal digits using the view's length, while the wrapper returns true without a hook because no shard suffix is required. Keep the routing-name and worker-function gates separate from that default and retain the required coordinator-dispatch hook. Always return afterward so the anchor does not enter collection/index/point-read planning. The distribution provider must reject unsuffixed logical routing tables and similarly named tables. Use cached namespace OIDs and trusted extension-owned naming, not a per-query shard-metadata scan, generic numeric suffix parser, or redundant shard-name check.
- Exercise the real worker-to-coordinator path with an empty routing table, caller rollback, original error propagation, EXECUTE denial, and nested-setting restoration. Verify provisioning, idempotence, coordinator-only placement, public SELECT without public writes, lookalike rejection, and ordinary collection dispatch. A direct same-backend helper alone does not establish distributed routing or transaction participation.

## Distributed Planning, Pushdown, and Upgrades

For changes to query construction, routing, pushdown, distributed DML, or extension upgrades, check which work runs on the coordinator and workers, what data they exchange, and which versions they can run together:

- **Placement and routing:** Identify which affected data and metadata tables are local, distributed, or reference tables, where each operation runs, and which routing or colocation assumptions it uses. Verify those assumptions against the actual table definitions and callers. Do not equate sharded/unsharded collection status with remote/local execution or infer reference-table behavior from a single-node test.
- **Cross-node object identity:** Apply the [name-based identity rules](documentdb-common.instructions.md#cross-node-object-identity) and read the [multinode identity-test requirements](../skills/test-documentdb/SKILL.md#test-authoring-and-behavioral-coverage). Trace serialized requests/responses, cursor state, execution-user propagation, and reference-table definitions, writers, migrations, and readers. Passing or storing node-local catalog OIDs as portable identities is an **error**.
- **Shard-aware predicates:** Reuse existing match/qual builders that already handle shard keys and object IDs rather than rebuilding those filters. Check that the selected helper also preserves the required expression, collation, and routing. If it cannot be used, explain which required behavior it lacks.
- **Pushdown boundary:** Follow the original batch or document payload through parsing, validation, copying, serialization, and materialization on both coordinator and worker. Compare sibling insert/update paths. Flag avoidable full-batch copies or duplicate coordinator work when the existing pushdown pattern can preserve the original payload and defer per-operation work to the worker. Do not move required validation or change error/ordering semantics merely to eliminate a copy.
- **Execution-path coverage:** Select focused cases for the distinct affected paths: sharded and unsharded collections, single-node and multinode deployments, local and remote execution, and relevant cursor/GetMore or feature-GUC variants. Do not require the full Cartesian product or distributed tests for purely local logic. Conversely, a local-only pass does not prove a worker path ran; use the owning suite's remote-execution controls when that boundary is the subject of the change.
- **Mixed-version upgrades:** Identify who installs binaries, who upgrades each node's schema, whether DDL reaches one node or is sent to others, and what must finish before the cluster is marked upgraded. Check single-node deployments, mixed binary/schema versions, and safe retries. Reuse topology/version helpers only if they work while versions differ; do not require a helper that calls an unavailable or incompatible SQL function. Determine node ordering from the upgrade code rather than assuming coordinator-first or worker-first.
- **Statistics and metadata locks:** Apply the backend [statistics-preservation rules](documentdb.instructions.md#mutation-design-and-validation). Verify that the reproducer calls the changed helper, including collection creation performed as part of another command, and that statistics remain configured and work afterward.

Report proven wrong routing, dropped shard predicates, duplicated side effects, unsafe upgrade ordering, or missing coverage of a changed distributed behavior as **errors**. Treat demonstrably avoidable batch copying/materialization as a **warning**. Keep an explicitly accepted performance follow-up separate from a correctness blocker, especially for a narrowly scoped hotfix.

## Aggregate Serialization Coverage

When a group aggregate's transition or combine function uses a custom state type (e.g., `BsonAggValue`), Citus can bypass the type's `_send`/`_receive` (serialization/deserialization) functions if `citus.enable_local_execution` is on (the default), because the aggregate state is never shipped across nodes. Distributed tests for such aggregates **must** include `SET citus.enable_local_execution TO OFF` to force remote execution and exercise the serialization/deserialization path. If a PR adds or modifies a group aggregate that returns a custom type and the accompanying distributed test does not disable local execution, flag it as a ⚠️ warning.
